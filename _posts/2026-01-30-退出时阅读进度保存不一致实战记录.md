在开发 EPUB 阅读器的过程中，阅读进度的“最后一次保存”往往是最容易出问题的地方。最近我处理了一个用户反馈：偶尔会出现进度恢复不准确，或者在调试日志中看到保存动作“离奇失效”。

本文将记录我如何从怀疑数据源开始，一步步深入底层协程和生命周期，最终定位并解决这个问题的全过程。

## 核心架构背景

在我的阅读器中，进度持久化链路如下：

1. **ReaderProgressSynchronizer**：监听 Readium 引擎的 Locator 变化，实时更新内存 Store。
2. **LocateStore**：内存快照，持有当前最新位置、版本号 `$v$` 以及 `dirty` 状态。
3. **AsyncProgressSaver**：负责将快照通过协程写入数据库（IO 线程）。

## 第一阶段：排查数据源 —— Flow 是实时的吗？

最开始，我直觉地怀疑是**数据源出了问题**。是否是因为在退出页面时，上游的 Flow 已经停止工作，导致我们拿到的位置信息是旧的，甚至根本拿不到数据？

我针对生命周期做了详细的排查：

- 检查了同步逻辑挂载的 `Lifecycle.State`。
- 在 `Flow.collect` 的出口和 `onStop` 回调中增加了对比日志。

**结论：** 日志显示，直到 `onStop` 触发的一刻，Flow 依然在下发最新的数据。这说明**数据源是健康的**，问题出在数据“流向”数据库的最后一段路上。

## 第二阶段：线索一 —— `JobCancellationException`

在排除数据源后，我在日志中捕获到了第一个关键信息：

`kotlinx.coroutines.JobCancellationException: Job was cancelled`

### 现象分析

这条日志说明协程在执行过程中被强行取消了。

我们的保存逻辑通常写在 `lifecycleScope.launch { ... }` 中。当用户退出页面时，`Fragment/Activity` 走向 `destroy`，关联的生命周期作用域会被自动 `cancel`。

如果此时“最后一次保存”的协程刚刚启动，或者还在 IO 线程排队，它会随着作用域的销毁而直接中断。这解释了为什么有时候保存看起来“没生效”。

### 初步修复

为了保证退出时的保存流程不被中断，我将其放入了 `NonCancellable` 上下文中执行：

```
// 伪代码示例
lifecycleScope.launch {
    withContext(NonCancellable) {
        saveProgress(APP_LIFECYCLE)
    }
}
```

## 第三阶段：线索二 —— 版本不一致与并发噪音

解决了取消问题后，日志变得完整了，但我却发现了一段诡异的序列：

1. `onStop begin` (dirty=true, v=3)
2. `onDestroyView begin` (dirty=true, v=3)
3. `save start` (reason=APP_LIFECYCLE, v=4)
4. `save start` (reason=APP_LIFECYCLE, v=5)
5. `markPersisted ignored: want=4, current=5`
6. `save ok` (v=4)
7. `markPersisted ok` (v=5)

### 根因总结

这里暴露了两个深层问题：

1. **生命周期重叠触发**：在 Android 中，`onStop` 和 `onDestroyView` 触发的时间点非常接近。如果两处都写了“确保同步并保存”的逻辑，就会在退出瞬间主动制造**并发竞争**。
2. **数据一致性风险**：这种并发行为不仅会导致多余的 IO 开销，更严重的是，**数据并不总是正确的**。由于两个流程几乎同时读取 Store 又分别写入，版本防御机制虽然能拦截一部分旧数据，但在极端的调度环境下，经常会出现状态标记混乱（例如由于 `markPersisted` 被 ignore，导致 Store 认为数据一直是 dirty，而在随后的清理中可能意外回滚或丢失真正的最新位置）。

## 最终修复：单飞机制（Single-Flight）

解决“保存不一致”的重点不在于让 `ignored` 日志消失，而在于：**退出保存流程必须是幂等的，且全局只能串行执行一次。**

我采用了以下组合方案：

1. **原子化 Job 守护（Atomic Guard）**：引入一个基于原子引用的 `exitSaveJob`（如 `AtomicReference<Job?>`）。利用原子化的 **Compare-and-Set (CAS)** 操作确保一旦 `onStop` 成功发起了保存任务，后续（如 `onDestroyView`）的触发将无法修改或重新开启任务，从而彻底阻断并发。
2. **引用快照化**：在启动退出保存时，立即捕获当前的 `Navigator`、`Store` 等必要组件引用。避免在 `NonCancellable` 执行期间，由于页面销毁导致字段被置空或替换。
3. **保持 NonCancellable**：继续保留非取消上下文，确保这一路“单飞”的 Job 能够完整落地。

## 经验教训

1. **重新认识异常**：在协程中，`JobCancellationException` 往往不是业务错误，而是结构化并发产生的“信号”。处理“临终保存”逻辑时，必须考虑跳出原有的生命周期作用域。
2. **警惕生命周期回调**：不要假设 `onStop`、`onSaveInstanceState` 或 `onDestroy` 是互斥的。它们在不同版本和操作下可能重叠触发。
3. **消除并发源，而非修补结果**：通过版本控制（Version Control）拦截旧数据写入是正确的防御，但更彻底的修复是确保在入口处就消灭不必要的并发请求。

希望这次实战记录能给正在处理 Android 数据持久化的开发者提供一些启发。在处理“最后一次写入”时，优雅的退出比快速的退出更重要。
